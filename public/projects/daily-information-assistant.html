A daily information assistant built around modular automation.

A lightweight personal information system that turns a Telegram message into a routed, context-aware answer — combining AI intent detection, external APIs, RSS feeds, Google Sheets, and purpose-built processing paths.

01 / Design Philosophy

Automation should reduce complexity, not hide it.

The system was built around a simple idea: AI should handle interpretation, while deterministic systems handle deterministic work. The workflow keeps access control, routing, data retrieval, and transformations explicit, then uses AI where it adds the most value — understanding intent, interpreting information, and turning results into useful responses.

Keep the architecture modular Each information domain has its own path, so a change to weather does not require rebuilding finance or news.
Use AI selectively Models are useful for interpretation and communication, but they are not always the right place for calculations or raw-data processing.
Move computation to the right layer For finance, repeatable calculations and summaries are prepared in Google Sheets so the agent can retrieve concise results instead of carrying the entire computational burden.
Design for failure Not every message will match a predefined intent. The fallback agent gives unmatched requests somewhere sensible to go instead of letting the conversation become a dead end.

The constraint shaped the architecture.

Lightweight and free-tier models were not always reliable for heavier financial processing. Instead of treating that as a model-selection problem alone, the workflow was designed around it: prepare what can be prepared ahead of time, then let the model focus on interpretation and communication.

02 / Architecture

One entry point. Several specialized paths.

The workflow starts with Telegram, validates who is allowed to interact with the bot, then uses an AI agent to understand the request and route it to the module that can answer it. The architecture keeps each information source independent while sharing the same conversational layer.

Full workflow architecture — the system is organized as a central routing layer with independent information modules.
03 / Request lifecycle

From message to answer.

The workflow is deliberately simple at the surface: send a message, identify what it means, run the appropriate data pipeline, and return a response through the same channel.

01

Gate the request

Incoming Telegram messages pass through an access check before they can reach the AI layer. The workflow accepts only the configured user identity and returns a generic rejection to unauthorized attempts.

02

Understand intent

An AI agent interprets the request and chooses the appropriate route. A switch then separates structured requests from conversational fallbacks.

03

Resolve and respond

The selected module gathers or retrieves the relevant information, formats it for a human response, and sends the result back to Telegram.

04 / Routing layer

The control plane stays intentionally small.

The central workflow handles the parts that should be shared: message intake, filtering, intent detection, routing, memory, and response delivery. The specialized modules own the domain-specific work.

Core routing layer — Telegram intake, access checks, intent classification, switch-based routing, and shared model/memory connections.
05 / Modules

Three focused information pipelines.

Each module has a narrow responsibility. That makes the workflow easier to debug, easier to change, and less dependent on one large AI prompt doing everything.

☁

Weather

API data → transformation → AI interpretation → Telegram

The weather path pulls forecast data from OpenWeather, performs a JavaScript transformation, and passes the result to an AI agent. The model turns raw forecast information into a readable answer before it is delivered through Telegram. The agent is connected to both Gemini and DeepSeek, giving the workflow flexibility around model capability and availability.

Weather module — external forecast data is normalized before AI interpretation.
◌

Current Events

RSS feeds → filtering → merge → LLM synthesis → Telegram

News requests are handled through two curated RSS sources. Each feed is limited before the results are merged, keeping the downstream prompt compact. A basic LLM chain then interprets the combined material, followed by another formatting and synthesis step before the final message is sent. The result is a focused news response rather than a raw list of headlines.

Current Events module — two curated feeds are combined and processed before delivery.
▦

Finance Analytics

Prepared sheets → AI agent + tools → Telegram

Finance queries take a different approach. Instead of asking a lightweight AI model to calculate everything from raw financial data, the workflow exposes prepared Google Sheets outputs as tools. The agent can retrieve running-balance, incoming, outgoing, summary, and forecast information, with a calculator available for smaller calculations. This keeps the daily interaction responsive without pushing expensive computation into the model.

Finance module — the AI agent retrieves prepared analytics from separate Google Sheets tools.
06 / Engineering challenges

Most of the work was in the seams.

The hard problems were less about drawing the workflow and more about making independent nodes behave like one reliable system.

Data transmittal between nodes

Structured payloads did not always survive cleanly between modules. JSON and text serialization created brittle handoffs, so inputs and outputs had to be inspected and normalized as the workflow evolved.

Matching models to tasks

Gemini, OpenRouter, HuggingFace, and other model options behaved differently under the same workload. The workflow became an exercise in matching model capability to the job rather than choosing one model for everything.

Workflow stability

Failures often appeared at module boundaries: an unexpected field, an incompatible format, or a message that did not match an intended route. Fallback handling became part of the architecture rather than an afterthought.

Optimization under practical limits

Finance forecasting and aggregation could be expensive for lightweight AI models. Moving repeatable calculations into prepared sheets reduced the computational burden and kept the conversational layer focused.

07 / Outcome

A practical pattern for AI-assisted automation.

The result is not a chatbot that simply happens to connect to a few APIs. It is a small automation system with a defined control layer, specialized data pipelines, and clear boundaries around where AI is — and is not — useful.
